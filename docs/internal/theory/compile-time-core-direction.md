# 编译期核心方向：axiom 核心层围绕 Rust 编译器的能力重新设计

> **性质**：I1 层方向性设计草案（`docs/internal/theory/`，不入 git）。
> **触发**：讨论中的转向——axiom 核心层应围绕 Rust 编译器能力（宏、过程宏、类型系统、
> const 泛型等）设计；核心层的能力到**编译时被计算后为止**，用于提供分析、验证。
> **立场**：由于是新的设计讨论，**旧设计的任何语义都值得被怀疑**，包括一直被坚持的原则。
> **状态**：DRAFT —— 待与作者收敛后定稿。

---

## 1. 核心命题

> axiom 核心层 = **compile-time DSL + 验证器**：它的全部"智能"（分析、验证、
> 类型约束、图构造）在**编译期**耗尽；产物是**普通 Rust 代码**。
> axiom 没有"运行时"——只有"编译期"与"编译后"两段。
> 这天然满足零成本承诺（编译后无 axiom 对象），并彻底改变蓝图的存在形态。

**含义**：蓝图不再是"运行时值"（如旧 `DynamicTopology`），而是**编译期构造物**
（类型 + const + 宏生成的代码）。

---

## 2. Rust 编译器能力工具箱（axiom 核心层可用的机制）

| 编译器能力 | 现成机制 | axiom 能用它做什么 |
|---|---|---|
| 过程宏 | `proc-macro`（属性/派生/函数宏）、`syn`/`quote` | 解析蓝图语法、**编译期验证并 emit 错误**、生成展开后的普通 Rust |
| trait 系统 | 关联类型、泛型约束、sealed、marker、typestate | 类型级证明（非法组合=编译失败）；axiom 现有强项 |
| const 泛型 + const fn | 编译期常量计算、`const { }` | 编译期构造并求值蓝图（边表 / N 值 / 拓扑） |
| const eval | 常量求值上下文 | 编译期完成算术与部分验证 |
| 类型级编程 | 用 trait 模拟依赖类型（有限） | 编译期"图即类型"（受限于 stable） |

**关键判断**：过程宏 = 表达 + 验证的最高杠杆；const 泛型 = 编译期图的入口。
二者结合使蓝图为编译期一等对象。

---

## 3. 旧原则的重新审视（每一项都该被怀疑）

### 3.1 应保留（且在新方向下更稳）

| 原则 | 理由 |
|---|---|
| **零成本承诺** | "编译期后为止"直接保证编译后无 axiom 对象；等价于手写代码自动成立 |
| **trait 类型级证明** | 非法组合在类型层编译失败，是现有最强项之一 |
| **no_std 目标支持** | 纯编译期核心与目标平台无关（编译器在 host 运行） |

### 3.2 应推翻 / 重定义

| 原则 | 旧义 | 新方向的处置 |
|---|---|---|
| **字面零依赖** | 核心零依赖 | **重定义**："编译后零运行时依赖"，编译期依赖（`syn`/`quote` 等宏依赖）允许——过程宏生态几乎必然依赖它们 |
| **FanOutViaTee** | 拒绝隐式扇出 | **推翻**：宏可生成 N 路扇出，无需 Tee 树；多对多连接作为一等（衔接统一模型） |
| **运行时 validate_deep** | 对运行时值做验证，返回 `Result` | **升级**：违规改为函数宏 `compile_error!` / 类型编译失败（violation = 编译错误，非运行时检查） |
| **DynamicTopology / 值形态** | 蓝图 = 运行时值 | **被挑战**：类型级图 + const 边表成为候选形态 |

### 3.3 待协商（依赖取舍定夺）

| 原则 | 新方向的张力 |
|---|---|
| **`forbid(unsafe_code)`** | 编译期层无运行时，影响变小；保留代价低、是好承诺，但宏生成代码的 unsafe 纪律需另行约定 |
| **静态/动态分叉** | 保留精神，重述为"编译期可验证（静态）vs 编译期不可（留普通代码）" |
| **no_std 的"零依赖"叙事** | 若核心分化出 proc-macro crate，其依赖与运行时库依赖需分开声明 |

## 4. 新架构形态（编译期核心）

```
axiom 编译期层（宿主，在编译器里运行）
  ├─ 过程宏：解析蓝图语法 → 验证 → 生成展开代码 + emit 错误
  ├─ trait 系统：类型级约束（非法组合 = 编译失败）
  └─ const 泛型 / const fn：编译期构造并求值图（边表 / N 值 / 拓扑）
        │  所有智能在编译期耗尽
        ▼
生成的普通 Rust（目标，零 axiom 智能残留）
  ├─ 展开后的调用图 / 数据结构
  └─ 纯执行，与手写等价（零成本涌现）
```

**关键转移**：验证从"运行时对值做"变成"编译期由宏 / 类型 / const 做"——
违反蓝图规则 = 编译错误（`compile_error!`）或类型约束失败，而非运行时 `Result`。
分析"产品"从"运行时检查报告"变成"编译期定型的结构"。

---

## 5. 由此打开的验证/表达新可能

1. **蓝图即类型/const**：拓扑用类型参数或 const 图表达，`validate` 在编译期求值。
2. **过程宏做"结构 lint"**：宏可扫描蓝图声明，在编译期做"所有端口有使用 / 所有注册有实现"
   之类检查（此前独立扫描需 build script，现在可入宏）。
3. **多对多/广播/布线生成**：宏根据 fan-out= N 自动生成 N 路分发代码，无需 Tee 树。
4. **会话对偶编译期判定**：协议对偶在类型层配对，非法传输编译失败（衔接会话类型）。
5. **行为接口 / const 基准**：若行为等价（A5/T5）未来实现，用宏 + 测试在编译期收紧。

## 6. 开放问题（待收敛）

1. **蓝图形态**：类型级图 vs const 边表 vs 宏 DSL 的取舍？(三者可组合)
2. **验证位置**：类型约束（trait）与宏 emit 的职责边界——哪些用类型证明、哪些用宏检查？
3. **编译期依赖接受度**：是否接受 `syn/quote` 作为编译期依赖以换取过程宏能力？（否定旧字面零依赖）
4. **旧的"运行时适配器"是否仍需要**：若核心纯编译期，runtime/物理层是否彻底退为"普通 Rust 代码"而非"axiom 运行时对象"？

---

> **一句话**：axiom 核心层从"能画复杂度图的验证系统"转向"**编译期 DSL + 验证器**"——
> 围绕 Rust 编译器能力（宏/类型/const），在编译期耗尽全部智能，产出与手写等价的普通
> Rust。零成本承诺因此成为结构必然；FanOutViaTee、运行时 validate、字面零依赖等旧语义
> 被重新审视，多数在该方向下被推翻或重定义。
