## 1. 完备 vs 极小：概念层的「完」不是「少」

**完备（complete）——概念层性质，绝对的、逻辑/语义的**：
生成元集合的闭包 = 整个可描述的概念空间；没有场景落在描述力之外。
不关心用了多少元素，关心**边界是否被触及**（"概念空间能够触及边界"）。

**极小（minimal）——实现层性质，相对的、物理/工程的**：
"最短路径"思维——在**给定的生成能力之内**用最少的元素/最省的路径表达。
极小是完备达成之后的**二阶优化**，不是概念本身。

**关系**：极小优化"给定能力内的路径"，完备决定"能力本身够不够"。极小**不扩展生成能力**。

**分层法则**：

| 层级 | 法则 | 目标 |
|---|---|---|
| 概念层 | 求「完」 | 描述力触及边界；可增、可澄清，**不为减法而减法** |
| 实现层 | 求「简」 | 在概念完备的前提下，用最省、最清晰的路径实现 |

减法在实现层是对的（删冗余、合并重复），但**不能上溯到概念层**。概念层的问题只有两个：
"这个生成元的语义是否不可约？"（纯度）与"概念空间还有没有覆盖不到的点？"（完备）。
都不是"够不够少"。

**极小思维的危险**：完备性失败会被**误诊为效率问题**——"再精简一下也许就能描述了"。
但精简到空也描述不了缺失的点：缺的不是效率，是**生成能力**。

## 2. 完备性诊断：失败只有两类归因

当生成元集合遇到**完全无法描述的场景**时，先诊断，不急着加减。完备性失败只有两类归因：

| 诊断 | 特征 | 归因 | 修复路径 |
|---|---|---|---|
| **① 局部缺失** | 概念空间某点落在生成元闭包之外，但新生成元**可无冲突嵌入**既有定义 | 概念/代码层缺失（闭包未覆盖） | 在既有公理体系内**补一个生成元**（加法） |
| **② 基础冲突** | 新生成元与既有定义/体系**冲突**，无法在既有公理体系内嵌入 | 基本定义的问题（公理/体系自身） | **回溯基本定义**——数学/分析学思路，重审公理 |

**判据（一句话）**：新元素能否在既有定义体系内**无冲突嵌入**？
- 能 → ①，补生成元即可；
- 否 → ②，不是"加一个元素"能解决的，是**基本定义需要修订**——数学问题 / 分析学思路。

**要点**：
- ① 是"覆盖不足"，修复在**生成元层**（闭包扩张）。
- ② 是"体系与完备冲突"，修复在**基本定义层**（公理回溯）。② 绝不是"删掉冲突的新元素"
  能解决的——删了只是回避冲突，完备性缺失仍在；必须回到底层定义，问"既有公理是否
  本身就是完备的障碍"。与数学史同构：发现某性质与现有公理矛盾时，选择是**修公理**
  （平行公理之争 → 非欧几何），而非无视反例。
- 两条路径都**不涉及"减法"**（§1：极小≠完备）。

## 3. 组合子的本质：完备描述的基本单元

组合子不是"支撑概念的集合元素"与"某个元对象的变体"二选一，而是**两者兼备**，分三个层面：

1. **元对象层**：存在唯一的抽象锚点（在 axiom 里是 `PortCell`，定义最小系统的形态
   `(S, I, O, step)`）。一切组合子都是它的实例。
2. **生成元层**：组合子是**封闭集合元素**——不可再分的原始组合能力（如
   `Wire`/`Chain`/`Choice`/`Opt`/`Merge`/`Feedback`/`Rep`/`Slot`/`Broadcast`）。
   同时每个都是元对象的**变体**（都 `impl PortCell`）。两者互补：正因为都是同一元对象的
   实例，才能被统一组合；正因为是封闭生成元集合，才能表达一切拓扑。
3. **表达层**：架构图 = 组合子的代数表达式 = 一个类型。图是表达式，运行是对同一表达式的
   求值；语法封闭 → 编译期可证，语义确定 → 运行符合图。

**"组合子"命名之真意**（源自 SKI 组合子逻辑）：**本身是系统，组合后仍是系统——组合封闭性**。
这保证复杂系统 = 简单子系统的组合，而组合结果仍是同类系统，每层可独立验证。

**定义（修正版）**：组合子 = **完备描述的基本单元**。完备是第一性质，极小只是完备达成后
可选的美学，不是定义的一部分。

**理想**：架构图语义 ≈ 运行效果语义，而非自底向上淹没在复杂度里。由**形状-内容分离**
（图是编译期可证对象）+ **组合封闭**（复杂度是嵌套出来的，不是抹平出来的）两条机制保证。
axiom 把"自底向上淹没"替换为"自顶向下嵌套在封闭类型里"。

## 4. 证明本体论：四种诚实模态与证明预算

回答反复出现的判断题："这个性质该不该交给编译期证明？"
**证明是昂贵的断言**——受可判定性、判定成本、判定价值三重约束。美学不是"一切都被证明"，
而是"每个声明都带着它真实的证明状态"。

| 模态 | 信任来源 | 成本 | 适用 |
|---|---|---|---|
| **① 结构强制** | 编译器（类型结构使非法不可表示） | 类型检查免费 | 可判定 ∧ 廉价 ∧ 错误代价高 |
| **② 编译期 const 见证** | 编译器（`const assert` / 关联常量） | 小 | 静态可判定 ∧ 廉价 |
| **③ 部署期/运行期校验** | 校验器 | 中 | 与部署策略相关 ∨ 聚合多个事实 |
| **④ 显式声明（公理）** | 声明者 | 零 | 语义性质不可判定（Rice 划界）∨ 证明成本 > 价值 |

**伪装 ＝ 把 ③/④ 说成 ①/②**——偷走前者的可信度却不付其税。伪装（而非"未证明"）
才是唯一的美学禁区。④ 的诚实形态：命名不冒充验证（`declare_*` 而非 `assert_*`）、
无伪默认值、文档明示"由声明者承担"。

**证明预算原则**：
1. 值得编译期证明 ⟺ 可判定 ∧ 成本可接受 ∧ 价值为正。
2. 预算范围：封闭概念边界内的类型平面 / const 平面性质走 ①②（零成本承诺的来源）；
   部署策略性质走 ③ 并显式标注；语义性质只允许 ④。
3. **最早期时刻原则**：性质的验证时机 = 该性质最早可判定的时刻。
4. **total 性偏好**：构造子类型应当 total（任何参数化都是合法蓝图）；约束优先表达为
   可选见证或独立类型，避免带隐式前置条件的 partial 类型（悬置态比合法/非法都更糟）。

## 5. 信任移交美学：结构的诚实

一切"声明 vs 强制"问题的共同根：**axiom 的本质是把信任从运行时/用户移交到编译器。**
每一个"声明而非强制"的地方，都是一次"把信任又悄悄塞回用户/运行时手里"的时刻。

六类典型的回退（及其诊断）：
1. **空 marker**：无证明义务的 trait，空 impl 即绕过 → 本应 ④ 却伪装成 ①。
2. **命名盗用**：已被数学语义占据的词（如 Kleene 星）指代不同语义 → 读者惯性被背叛。
3. **见证只护单路径**：良构性外挂到某个仪式方法，绕路即静默通过 → 半模态比单模态更糟。
4. **可编译期判定的错误推迟到运行期** → 验证时机的退行。
5. **内容层能力漏进形状层**（如扇出要求值可拷贝）→ 层污染，是原理还是实现需判别。
6. **证据链自污染**（未优化的测量混入验收命令）→ 假警报训练读者忽略所有警报。

**审美原则**：好的抽象是"结构替你诚实"——它不需要你记得、不需要你承诺、不需要你分辨。
目标是让"正确性"与"零成本"成为**结构的内置属性**，而非**用户的纪律**。

## 6. 信任移交的美学边界（本体论）

不是所有问题都值得交给编译器证明——编译器能力与编码能力有限、有边界：

- 鼓励**可证明的问题**交给编译器（花算力代价计算）；
- 但"所有问题都能编译器做"不成立（可判定性边界，如 Rice）；
- 且有的问题**不值得被证明**（证明成本 > 价值）。

axiom 的承诺修正为：在封闭概念边界内，把**可判定的、廉价的、高价值的**性质用结构强制
（①②）；其余性质**诚实落 ③/④，绝不伪装**。判定器决定"值不值得证明"，axiom 决定
"证明了就绝不装没证明，没证明就绝不说证明了"。

## 7. 三层边界：证明 → 框架 → 契约（信息传递的本体）

"信息传递是物理层自己的事情，无法在 core 内定义"——精确表述是三层衰减，不是二分：

1. **core（证明层）**：类型系统强制形状（可判定），**无契约**。
2. **runtime 框架（容纳层）**：trait 接口容纳一切传递方式，提供部署期校验（模态 ③，
   半契约）；具体传递方式可替换、可不用，axiom 提供**参考实现**而非唯一/强制实现。
3. **开发者（契约层）**：具体载体的传递语义（不丢消息/FIFO/背压/线程安全）**不可判定、
   无法约束**，是模态 ④ 的纸面契约。

**边界是衰减谱不是一刀切**："无法在 core 内定义" ≠ "axiom 什么也不管"——
runtime 提供框架与部署期校验，只是不提供"证明具体传递语义"。纸面契约不是 axiom 的失败，
是 axiom 对"类型系统本性边界"的诚实尊重。

## 8. 系统 / 模块的三态定义：本体 · 退化 · 构造

**为什么需要三态**：单说"系统 ≠ 函数"不够——类型论上系统可以退化为函数（`S = ()`），
异步语境下可能通过异步函数开始一个模块的生命周期。两个合法事实悬空，就会不断制造
"系统到底是不是函数"的摇摆。三态把退化关系显式纳入定义。

### 8.1 三态结构

**① 本体态：最小系统（完整、一般形态）**

```
最小系统 = (S, I, O, δ)，δ : S × I → S × O
- S = 跨激活存活的状态容器（资源持有者）
- I/O = 信息传递接口（广义，见 §8.4）
- 生命周期独立于任何单次服务
```

**模块 = 资源的持有者 + 服务的提供者**（manager / scheduler / server / controller /
tensor-compute）。模块"做的一件事"是**管理一类资源 / 提供一类服务**（管理内存、调度任务、
服务请求、控制被控对象、管理计算存储），不是"执行一个数据变换"。

**② 退化态：`S = ()` 时，代数上退化为函数**

```
当 S = ()（无状态容器）时：δ : I → O  —— 纯函数形态
```

这是类型论意义上的**特例化（specialization）**。一个模块若只做"两个整数相加"，它的
几乎一切语义、定义、功能就是一个 `fn add(a: i32, b: i32) -> i32`——**模块/系统的语义
完整地、无损地退化为函数**，函数是这个模块的**完备承载**（没有丢失任何东西）。

**③ 构造态：异步函数作为模块入口**

```
async fn serve(...) { ... }   // 函数的生命周期在此开始
     ↕
模块（服务实体）：serve 启动后常驻运行、持有资源、持续服务
```

异步函数是模块的**出生方式 / 入口**，不是模块本身。`serve` 调用返回后**模块仍在运行**
（它启动的常驻服务体活着）；函数只是"点燃生命周期的那次调用"。

### 8.2 函数 ⊂ 系统：退化是完备承载，反向包含是不完备

| | 退化态（S=()） | 构造态（async fn 入口） |
|---|---|---|
| **退化什么** | 系统的**状态容器**退化（S→()） | 系统被一个**函数入口**启动 |
| **结果** | 代数上系统 = 无状态系统 = 函数形态 | 函数启动模块，但模块≠函数 |
| **不改变什么** | 定义仍是 (S,I,O,δ)，只是 S=() | 模块的生命周期/资源持有仍在 |
| **概念上** | "无状态系统"仍是系统 | "由函数启动的模块"仍是模块 |

**包含关系**：

- **函数 ⊂ 系统**（函数是系统的子集：`S=()` 的退化形态）。
- 模块若只做 `add`，它**正好落在子集里**——退化为函数且无损。
- 但系统整体大于函数：有状态模块（`S≠()`，如分配器状态）、常驻服务（生命周期独立）、
  组合（`Chain`/`Merge`/`Feedback`/`Broadcast`，函数组合只是 `Wire`/`Chain` 的特例）、
  资源持有、广义信息传递——全在子集之外。

**精确断言**：

```
模块 ⟶ 退化 ⟹ 函数（完备，无损）
函数 ⟶ 包含 ⟹ 系统（不完备，系统更大）
```

**"退化"是完备承载**（无损），不是"近似"——`add` 模块退化为 `fn add`，函数完全表达了
它的一切；反过来"系统 = 函数"则是**不完备包含**（丢掉子集外的部分）。所以：

> **函数是系统的退化子集（S=() 时），不是系统的同义词。模块可以是函数，函数不总是模块。**

### 8.3 这纠正了什么

曾出现的错误：把"退化态/构造态"当成"本体态"——把无状态的变换步骤（归一化、告警阈值、
支付受理）直接当成"模块"。正确理解：

> 无状态变换步骤是"退化态"的系统（`S=()` 下），或是模块之间的处理流；**系统本体是
> 持有资源、提供服务、生命周期常驻的实体**。模块之间的边携带的值，接收端可解释为
> 数据/命令/观测，但**物理上都是信息传递**（§8.4）。

### 8.4 I/O = 信息传递（广义），服务/命令是抽象层语义

"模块的 I/O 是服务/命令/请求-响应，不是数据流的输入输出"——此表述有歧义，需修正：

**物理层（统一）**：I/O = 信息传递的方式（广义，非 OS 概念）。最简单的形式就是一个
变量的修改——**某个地址指向的字节被修改**。信息并没有"从物理位置 A 搬运到位置 B"，
只是**同一共享位置的字节状态被改写/被读取**。在这个意义上，**"服务请求"和"数据流输入"
在物理层是同一件事**——不存在"服务 I/O"与"数据流 I/O"之分。

**抽象层（语义）**：服务/命令/请求-响应是**接收端如何解释这个值**的语义注解，不是物理
层的 I/O 种类。这与 FlowKind（Data/Control/Observe）同构：物理层统一为信息传递，
抽象层才区分"这值是数据、命令还是观测"。

**修正表述**：

> 模块的 I/O 在**物理层**与任何其他 I/O 一样——都是信息传递（字节被修改）；区别只在
> **抽象层**：模块 I/O 携带的值被接收端解释为**服务请求/命令**，而"数据流"的值被解释为
> **待处理的数据**。这是语义解释的差异，不是物理机制的差异。

模块的"服务性"不在于物理上有一种特殊的 I/O，而在于**它在抽象层被解释为一个服务提供者**
——接收端以"调用/被服务"的方式理解流入的值。

### 8.5 双层关系：物理层等价 / 抽象层包含，身份为分界

**代码定义上的同一性**：函数和模块在代码上**都可以编码为"可调用的执行体"**（正如 Rust
用 `Fn`/`FnMut` trait 统一函数与闭包）：

```
函数   : fn(I) -> O                          （无状态，一次调用）
模块   : fn step(S, I) -> (S, O)            （有状态，多次调用，状态显式进出）
```

模块的 `step` **就是**一个函数。所以在"代码定义"层面——**它们是同一种东西**：都是
"从输入到输出的转移函数"。区别只在于**这个函数被调用时，是否带一个跨调用存活的状态 S**。

**身份（identity）是分界线**：

| | 函数 `fn(I)->O` | 模块 `(S,I,O,δ)` |
|---|---|---|
| **状态** | S = ()（无跨调用状态） | S ≠ ()（跨调用存活） |
| **身份** | **无身份**——`add(1,2)` 与 `add(1,2)` 不可区分，匿名的一次计算 | **有身份**——同一个 `&mut self` 被反复调用，状态在调用间传递，是**同一主体在行动** |
| **调用** | 单次即完成 | 多次、多样、可按 if 分派 |
| **物理层** | 压栈/弹栈（资源分配/回收） | 构造/运行/析构（同样的物理动作，放大版） |

**"一定程度" = S 从 `()` 变成非 `()` 的时刻**。当任务需要**跨调用的记忆**（状态）和
**可区分的同一性**（身份），单次匿名函数就装不下了，必须升级为模块。

**物理层等价**：模块在运行时因 if 被创建/释放，**从物理层看确实就是函数行为**：

```
创建 = 分配 S 的资源（初始化状态）—— 物理层动作
释放 = 回收 S 的资源（析构状态）  —— 物理层动作
```

这与函数调用的**压栈（进入分配）→ 执行 → 弹栈（退出回收）在物理上完全同构**——都是
"资源的分配与回收"。精确表述：

> **模块的一次完整生命周期（创建→运行→释放）从物理层看，就是一次"放大的函数调用"**——
> 进入分配、运行、退出释放。模块是"慢放的函数"，函数是"瞬时的模块"。

呼应物理层统一性：物理层只有"值流经结构 + 资源分配/回收"，没有"函数 vs 模块"之分；
区别完全在抽象层（身份/状态/组合）。

**双层关系（不是单层包含）**：

```
物理层：函数调用  ≈  模块生命周期
        (分配→执行→回收) ≡ (创建→运行→释放)
        都是"资源的分配与回收"——同一类物理动作

抽象层：函数 ⊂ 模块（S=() 的系统）
        模块 = 函数 + 状态(S) + 身份 + 常驻 + 组合 + 广义信息传递
```

- **物理层**：函数 ≈ 模块（等价）——都是资源的分配与回收
- **抽象层**：函数 ⊂ 模块（包含）——模块多出状态/身份/常驻/组合维度

> **结论**：函数与模块在代码上同为"可调用执行体"，在物理层等价（资源分配/回收），
> 在抽象层包含（模块多出状态、身份、常驻、组合维度）。"单次调用"是函数的本体；
> "多次调用 + 跨调用状态"是模块的本体。两者共享物理动作，区别在抽象语义。
> 集合关系是**双层**的：物理层同一、抽象层包含——同时成立，取决于在哪一层看。
