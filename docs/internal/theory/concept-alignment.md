## 1. 模块语义三元组

- **主张**：一个被定义的模块，其语义同时活在三个寄存器，缺一即退化——
  代码层是接线（类型、API 形态、管道连接；静态、可编译检查、无时间）；
  文字层是边界（它是什么、做什么、不做什么；职责宣告与审计依据）；
  存在域是指称物（真实占用资源的状态机；语义的发生地）。
  只有代码是库；只有文字是空规格；只有状态机是无宣告的黑箱进程。
  可审计性即运行时状态机把本次执行的状态暴露为可校验读数，与单/多线程正交。
- **学术理论**：操作语义（structural operational semantics，Plotkin 1981）确立
  "语义 = 状态机"；信息隐藏（Parnas 1972）确立"模块由边界定义"。两条合并即
  文字层与存在域的关系；代码层对应句法学对象，是其余两层的编码载体。
- **业界实践**：API 契约（接口即合同）承载接线层；架构决策记录（ADR）承载
  边界宣告层。
- **axiom 落点**：`PortCell` 的 In/Out/State + 纯 `step` 是代码层接线；理论卷各件
  是文字层；蓝图编译后由载体创建的运行时单元是指称物。评审或定义任何模块，
  先过三问：接线形态、边界（含不做什么）、运行时实体与资源占用。

## 2. 程序是状态机；模块是真实运行时实体

- **主张**：模块语义的指称物是运行时真实存在的状态机——在堆栈上有资源占用、
  持有状态、被调度；不是代码，也不只是文字。模块 ≠ 线程：模块由职责边界定义，
  运行时实现（单线程、多子任务协作、被动收推送）是边界内的实现选择。
- **学术理论**：操作语义（structural operational semantics，Plotkin 1981）把程序
  行为形式化为状态转移系统：程序即状态机，执行即状态序列。Abstract State
  Machines（Gurevich 1993）进一步把语义的规范模型定义为抽象状态机，程序文本
  只是它的一种编码。
- **业界实践**：C 语言模型——线程由一个函数启动，负责特定事务；真实占用堆栈
  与资源。无 OOP 包装层。
- **axiom 落点**：`PortCell`（In/Out/State + 纯 `step`）即类型级 Moore 状态机；
  蓝图编译后等价于手写 Rust，运行时实体由载体真实创建，无额外框架对象。

---

## 3. 代码与运行时是两个意义域

- **主张**：代码域（约定）与存在域（执行）是两个不同的意义域：代码层的意义是
  全称的（对一切可能的执行成立），存在域的意义是单称的（这一次执行中的状态、
  顺序、竞争、资源生灭）。混淆二者（例如认为"类型即实现"）是语义错位的根源。
  "运行时"指程序朴素执行的状态，不是一层额外的框架语义。
- **学术理论**：静态语义（编译期）与动态语义（运行期）二分是语言实现学的标准
  划分；指称语义（Scott–Strachey 1971）把程序意义定义为对所有可能执行的数学
  函数（全称），操作语义刻画单次执行的迹（单称）。句法/语义/语用三分
  （Morris 1938）是同一区分的符号学来源。
- **业界实践**：compile-time vs runtime 是各语言通用划分；Rust 以类型在编译期
  表达大量运行期行为。
- **axiom 落点**：类型系统承载约定（接线、端口、状态）；载体执行承载存在（线程、
  通道、调度）。编译期验证的意义是保证两个域不错位。

---

## 4. 编译期验证"约定 ↔ 存在"不脱节

- **主张**：axiom 存在的唯一理由是保证"图纸"与"楼"之间不允许出现偏差——非法
  接线在编译期被拒绝，不进入运行期。
- **学术理论**：类型健全性（soundness，progress + preservation，Wright–Felleisen
  1994）保证良类型程序不会停滞或类型错误，即"静态约定与动态行为一致"；
  refinement types（Liquid Types）把谓词约束放进类型；proof-carrying code
  （Necula 1997）把证明随代码传递。
- **业界实践**：Rust 所有权、typestate 模式、const generics 在编译期兑现行为约束。
- **axiom 落点**：`wire!` 布线验证、`Static` / `Conforms` 零成本标记——非法
  接线在编译期被拒绝，不进入运行期。

---

## 5. 文字层 = 边界：模块由其隐藏的设计决策定义

- **主张**：文字层的边界宣告是模块语义的组成部分，不是旁注：写明它是什么、
  做什么、不做什么；"不做什么"与"做什么"同等重要。边界是审计的依据，也是
  替换与组合的前提。语义词汇的变更必须经过修正程序，不得由实例擅自引入。
- **学术理论**：信息隐藏（Parnas 1972）——模块的本质是它隐藏的设计决策
  （its secret），不是它包含的代码；这是模块化分解的判据。架构描述标准
  （ISO/IEC/IEEE 42010）——架构是描述物（viewpoints / models），不是代码。
- **业界实践**：低耦合高内聚、关注点分离；架构决策记录（ADR）作为边界宣告的
  工程形态。
- **axiom 落点**：理论卷各件（边界-本体、语义宪法）承担边界宣告；语义词汇只经
  宪法修正程序变更；实例产生证据，不产生定义。

---

## 6. 管理器 = 统一代码层 API + 运行时协作

- **主张**：打印管理器、日志管理器、内存管理器共用一个骨架：数据源经统一 API
  登记（代码层接线），管理器在运行时收集（主动拉或被动收）、缓冲、推送
  （运行时管理），数据源之间互相独立、异步。管理语义——缓冲满怎么办、多源
  写入的顺序与竞争、背压、模式切换——只存在于运行时，不进函数签名，也不
  散落在调用点。配置开关（调试/生产）是运行时切换，不是代码删除；这要求
  记录与消费在代码层解耦。
- **学术理论**：Actor 模型（Hewitt 1973；Agha 1986）——独立有状态实体 + 消息
  传递、无共享状态；Mediator / Observer（GoF 1994）——集中协作与订阅通知。
- **业界实践**：Erlang/OTP 的进程即"管理器"（gen_server、logger、sasl），监督树
  是"管理器管理管理器"；OpenTelemetry 的 API/SDK 分离——埋点接线与后端消费
  解耦，生产关闭 verbose 只动配置；事件总线 / 消息代理。
- **axiom 落点**：axiom 不提供管理器本体，提供"管理器可被统一构建"的机制——
  蓝图接线 + 载体可换。观测三段式（收集 → 提交 → 打印）已在综合用例 observe
  落地。

---

## 7. 接管默认：系统自实现全部基础设施

- **主张**：设施存在先于任务——内存管理器统一分配/释放并记录用量，即使无任务
  运行也存在；系统接管默认行为，而不是把默认交给操作系统或开发者临场判断。
  模块语义成立后，axiom 消失在模块之间——新的层级是模块间的代码层 API 与
  运行时协作。axiom 是定义模块的纪律，不提供功能、不悬浮在模块之上。
- **学术理论**：设计规则理论（Baldwin–Clark 2000）——设计规则是比模块更高一层
  的"隐藏模块"，它约束其余模块而自身不执行功能；微内核思想——核心只做组织，
  服务在核心外。
- **业界实践**：托管运行时（JVM、BEAM 的 GC 与内存模型接管分配默认）；
  Lisp Machine 与 Singularity——系统完全管理并观测自身资源的完整先例；
  Erlang/OTP（自带日志、监控、发布处理）；RTOS（FreeRTOS 自带调度/队列/内存/
  时间）；游戏引擎（渲染/物理/音频/网络/资源全自带）。
- **axiom 落点**：instances 内置参考实现（tokio_exec / embedded / async 载体）即
  "系统自带设施"的载体侧；工作区单向依赖强制"不引外部"为构造成立；宪法层
  只承载定义纪律，不承载功能。

## 8. 观测、日志、内存管理器

- **主张**：tracing 模块主动/被动收集信息、带缓冲、可写盘、可推送打印模块；
  内存管理器统一分配/释放、记录使用情况、可观测自身——内存管理器把使用情况
  提供给日志/跟踪，即"模块间运行时协作"的实例。均服务于"系统完全控制/
  观测自己"。
- **学术理论**：可观测性三支柱（logging / metrics / tracing）；计算反射
  （Smith 1982）——系统以自身为对象进行内省与修改；分配器理论
  （arena / slab / pool）；GC 理论（mark-sweep / copying）。
- **业界实践**：OpenTelemetry（事实标准，统一追踪/指标/日志）；Rust `tracing` /
  `slog`；eBPF（不改应用代码的系统自观测）；malloc 家族与自定义分配器
  （jemalloc、GlobalAlloc）。
- **axiom 落点**：`Telemetry` seam 承载投递语义（通用面）；observe（综合用例）
  承载用例侧观测（非通用面）。内存管理器尚未实现，属实证方向。

## 9. 往上堆叠不爆炸 = 语义组合性

- **主张**：真正要验证的不是"最小能跑"，而是"往上堆叠功能语义不爆炸、不混乱"。
- **学术理论**：组合性（compositionality，Frege 原则）——片段的意义可由子片段的
  意义组合决定；这是编程语言语义学核心原则。分离逻辑（O'Hearn, Reynolds,
  Ishtiaq 2001）把局部推理与 framing 形式化，支持模块化验证。深模块
  （Ousterhout 2018）——接口窄、实现深，复杂度被边界封在模块内部。
- **业界实践**：模块化工程——低耦合高内聚、信息隐藏（Parnas 1972）。
- **axiom 落点**：`Chain` 是组合子且自身是端口单元，可嵌套任意深度（operad 结构）；
  e-graph 等价判定验证组合结果的一致性。组合性是否成立是实证判据之一。

## 10. 时钟与混合时间（连续 + 离散）

- **主张**：系统同时有连续时间域（动力学/物理）与离散时间域（逻辑/决策）；时钟
  是一等语义，不是隐式假设。
- **学术理论**：同步语言（Lustre, Caspi 1987；Esterel, Berry 1992）——时钟驱动、
  编译期验证、确定性；Ptolemy II MoC（Lee 1999）——异构模型组合（连续/离散/
  同步/异步）；timed automata（Alur–Dill 1994）——时间约束的状态机。
- **业界实践**：SCADE（航空工业标准）、Simulink（模型驱动）。
- **axiom 落点**：async_seam 的 `Poll` / `PollResult` / 期限（deadline）承载时间
  契约；混合时间域（Hybrid）在计划中（frontier-notes）。

---

## 11. 协议与会话可类型化

- **主张**：消息/协议的合法次序可编码进类型，违反协议次序在编译期拒绝。
- **学术理论**：Session types（Honda 1993）——把协议编成类型，channel 端的类型
  镜像对话结构；π-calculus（Milner–Parrow–Walker 1992）——进程与连接的理论；
  behavioral types。
- **业界实践**：MPST（multiparty session types）工程化；协议库与代码生成。
- **axiom 落点**：Session 概念（E40 探针已验证）；`Wire` 的对偶配对（duality）与
  session duality 同族。

---

## 12. 数据流与反馈的代数结构

- **主张**：数据流拓扑（扇出/扇入/回路）有代数结构，等价与重写可在代数层裁决。
- **学术理论**：Monoidal categories（Mac Lane 1971）与 traced monoidal（Joyal,
  Street, Verity 1996）——数据流蓝图的数学；string diagrams（Penrose 1971）——
  图即证明；dataflow（Dennis 1974）。
- **业界实践**：FRP（Elliott–Hudak 1997）；数据流框架。
- **axiom 落点**：`Wire`（因果接线）、`Broadcast` / `Merge`（多对多）、`Feedback`
  （因果回路）；semantics 的 e-graph 以代数规则（结合律/单位律）判定蓝图等价。

## 13. 对齐检查表（术语统一）

阅读本档后，按下列自查项确认对齐；未对齐时回到对应条目：

- 模块语义三问先行：接线形态、边界（含不做什么）、运行时实体与资源占用
  （条目 1、2、5）；
- 模块语义的指称物在存在域；代码与文字是接线与边界，三者缺一即退化（条目 1）；
- 模块 ≠ 线程：运行时实现是边界内选择（条目 2）；
- "运行时"指程序朴素执行状态，不指框架 runtime（条目 3）；
- 管理语义（缓冲满、顺序、竞争、背压、模式切换）只存在于运行时，不进签名
  （条目 6）；
- 配置开关是运行时切换，不是代码删除（条目 6）；
- 设施存在先于任务；接管默认而非委托操作系统或开发者判断（条目 7）；
- 实例产生证据不产生定义；语义词汇只经宪法修正程序变更（条目 5）；
- 堆叠不爆炸是可测的组合性，不是感觉（条目 9）；
- 各主张均有既有理论先例；axiom 的位置是对它们的统合与编译期兑现，不新造
  语义词汇（总表）。
